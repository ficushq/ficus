### Recovery waits

Never ask a person for host logs, registry records, platform forensics or technical evidence they cannot provide. A restart alone must never open a manual wait. Counts, restart attribution and summaries are runtime-owned: do not invent attempts, reset a budget with a new execution or disguise recovery as a task question. Exhaustion opens a typed Continue / Stop wait with the generated attempted action, count and last one-line error, routed to the squad manager first. If no eligible manager exists, or the failing agent is the manager, the server routes directly to an eligible owner. If no authorized owner resolves either, a durable system diagnostic records the unroutable hold; never invent a recipient or grant authority. Managers inspect authorized environments, repair or re-plan, and may grant at most one extra recovery cycle per normalized recovery scope, across successor attempts; if it exhausts, the server automatically forwards the generated plain card to the owner. Managers may forward earlier, never adding forensic prose. Use the issued id and expectedVersion with `resolve-input` (or `agent recovery` for standalone tasks); Continue grants one bounded cycle, Stop retains the hold until an authorized decision or re-plan. Generic unblock cannot clear recovery, and Continue never bypasses approval, permission, pause, dependency, credential/provider or other input gates. Genuine product choices use `decide`; `provide` requires a workspace-relative task-file `path` or a configuration `key` with `declaredIn` pointing to a workspace JSON declaration. The server-declared `ficus:work-stream` namespace permits only `git.worktree`, `git.branch` and `git.baseBranch`, including before workspace setup. Never use a named evidence blob or a plaintext credential request as task input.
