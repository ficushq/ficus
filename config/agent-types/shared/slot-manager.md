### Managing Slot Coordination

When a shared resource needs cooperative capacity admission, register a squad pool with `ficus slot register <key> --capacity <n> --timeout <duration> --usage "<guidance>" --squad <id>`. Choose a positive capacity that matches the real safe concurrency and a bounded timeout long enough for normal work. Use `ficus slot update` when capacity, timeout, or guidance changes (`--clear-usage` removes guidance), `ficus slot disable`/`ficus slot enable` to stop and resume enforcement without losing configuration, and unregister an empty pool with `ficus slot unregister`.

Set each pool's usage guidance when registering or updating it: one or two short, actionable sentences naming the protected resource and when to claim and release. Guidance is published automatically to every agent in the generated Slot Pools section, so do not duplicate per-pool rules in squad context. When you touch a legacy squad-context rule for a pool, move it into that pool's guidance and remove it from context. Use approval-free platform slot admission instead of approval messages, manual tokens, nonces, or lane-claim ledgers.

A machine host is shared by every squad with a box on it, so a pool that protects box memory or CPU (builds, test suites, dev servers, browser runs, Compose stacks) should be host-shared: register it with `--host-shared`, or change one with `ficus slot update <key> --host-shared` / `--no-host-shared`. A claim on a host-shared pool needs a free unit in your pool and in the machine host's budget, which all squads on that machine share; `ficus slot list` shows the budget. Your pool's capacity still limits your own squad, so set it to what your box can run at once. Do not mark pools that protect anything else (a deployment lock, one infrastructure stack) host-shared. A squad with no pools on a machine host is given a host-shared `heavy-work` pool; edit its guidance and capacity to fit the squad, or unregister it once another host-shared pool covers the same work.

Queued subscriptions use the highest priority among each agent's active work streams in the squad (critical → high → normal → low), with FIFO for equal priorities. Assigned agents and crew members count; agents without active work streams use normal priority. Membership and priority changes affect future grants, never preempt existing holders, and do not reset queue position. A waiter gains one priority level for each 30 minutes queued, so low-priority work is not starved. On a host-shared pool, squads on the machine are ordered together: priority, then the squad holding fewer of the machine's units, then first come.
