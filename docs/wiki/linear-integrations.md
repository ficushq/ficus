# Linear integration

Manage Linear in **Settings → Integrations → Linear**. One `linear` integration offers two kinds of connection, described in [Connections](#connections): the Ficus **agent app**, installed in a Linear workspace with OAuth, and a **personal API key**. Squad rules, team routing, tracked issues, outputs, the CLI and the skill are the same for both.

## Connections

A squad uses exactly one Linear connection, of either kind. Both kinds can exist on one instance; moving a squad from a key to the app is an ordinary reassignment in its Integrations tab, and tracked issues keep matching because they match on the Linear issue ID.

**The card.** Connections come first, one row each: the workspace name and URL key for an app connection (or the account name for an API key), its kind, one status badge (Healthy, Needs permissions, Reconnect required, Disabled and so on), at most one inline action that fixes that status (**Reconnect** or **Enable**), and a **More actions** menu with Validate, Reconnect or Replace API key, Disable… and Remove…. Disable and Remove ask for confirmation in the row and name how many squads lose access. Below the rows, **Install Ficus in Linear** is the primary action until a connection exists; after an app install it becomes the secondary **Install in another workspace**. The API-key form stays collapsed behind **Use a personal API key instead**. On a self-hosted instance the Linear application settings stay open until they are saved and then fold into **Linear application settings**. An install failure and a settings-save failure are each shown next to their own control, so an older save error cannot hide a newer install failure. The DB-free layout check renders every state with synthetic data at 1280 and 390 pixels, light and dark: from `apps/web`, run `CHROMIUM_PATH=/path/to/chromium bun scripts/check-linear-integration-layout.ts` (optional `SCREENSHOT_DIR` saves the screenshots).

**Agent app (OAuth).** Installable on every instance: installing is always offered in the Linear card, and `authorization/start` accepts `linear` under both client authorities. An install still needs its OAuth application. On Ficus Cloud, if Platform has no Linear application configured, the broker answers `503 broker_unconfigured` and Core returns `broker_unconfigured`, which the card explains. On a self-hosted instance, **Install Ficus in Linear** appears only after the operator saves the application's client ID, client secret and webhook signing secret; an install attempted without them fails with `oauth_app_unconfigured`. API-key connections are unaffected.

Ficus appears in the Linear workspace as its own app member, so people can delegate issues to it and mention it. **Install Ficus in Linear** opens Linear's consent page with `actor=app` and the scopes `read`, `write`, `app:assignable` and `app:mentionable`; a Linear workspace admin must approve it. `write` is needed because Linear refuses the agent mutations Ficus sends (`agentActivityCreate` for acknowledgments and progress, `agentSessionUpdate` for Open in Ficus, `agentSessionCreateOnIssue` for `--linear-session`, `attachmentLinkGitHubPR` for pull request attachments) under the narrower `issues:create` and `comments:create` with ``Invalid scope: `write` required``. **Reconnect** asks Linear to update the existing installation: the authorization URL carries `update_scopes_on_existing_token=true` with the complete scope set. Without it Linear leaves an existing installation's scopes unchanged, so an installation made with the older scope set gains `write` only through Reconnect. A self-hosted (local) Reconnect sends the parameter. A hosted Reconnect sends it only once the Platform broker passes the reconnect intent to the Linear adapter and carries this version of the shared adapter; until then, a hosted Reconnect does not upgrade an existing installation. The connection is named `<Workspace name> (Ficus app)` and identified by the Linear organization ID, so installing again in the same workspace (or **Reconnect** on the connection) updates the same connection instead of adding another one. Validation reads `viewer { id name app }` and `organization { id name urlKey }`, and fails with `workspace_identity_mismatch` unless the token's viewer is an app user with the stored app user ID in the stored organization; a person's own (`actor=user`) token is never accepted as an app connection. Workspace renames are picked up on the next validation.

App connections get the full OAuth lifecycle (see [Integration contracts](integration-contracts.md)). Linear access tokens last 24 hours and every refresh rotates the pair, so Ficus refreshes proactively before expiry, persists the new pair before validating it, and serializes refreshes per connection. A refresh that Linear refuses with `invalid_grant` marks the connection **Reconnect required**. An expired access token is never handed to a command. Removing or replacing an app connection revokes its access token. Revoking a token is token cleanup only: to remove the app from the workspace, uninstall it in Linear's settings.

- **Ficus Cloud:** the hosted Ficus app is used through the Platform OAuth broker; nothing needs configuring on the instance.
- **Self-hosted:** create your own OAuth application in Linear's API settings (it can have any name; it appears in Linear under that name). In the Linear card (inside **Linear application settings** once they are saved), Ficus shows the callback URL (`<public URL>/settings/integrations/oauth/callback/linear`) and the app webhook URL (`<public URL>/api/webhooks/linear-app`) to copy into that application. Enable webhooks with the categories Agent session events, Inbox notifications, Permission changes, Issues and Comments. Then save the application's client ID, client secret and webhook signing secret in Ficus and choose **Install Ficus in Linear**. Both secrets are stored encrypted in `__integration-oauth-app:linear` and are never returned; **Replace application settings** overwrites all three. App connections authorized by a previous client ID need **Reconnect** after it changes. The instance needs a public URL for the callback.

**Personal API key.** Create a named account with a personal API key, validate it, and enable the account. Keys can be limited to specific teams in Linear. Read access is enough for issue search and assignment routing; give the key write access as well (creating issues and comments) so agents can update issues with the [Linear CLI](#agent-cli). Validation proves only that the key can read, and is recorded as `issues:read`; a read-only key fails when an agent tries to write. API-key connections are never refreshed, revoked or expiry-checked, and the stored key is kept exactly as entered. See [Linear’s API documentation](https://linear.app/docs/api-and-webhooks).

**Credential shape.** An API-key connection stores the raw key and its configuration is `{ version: 1 }`. An app connection stores an OAuth credential bundle and its configuration is `{ version: 2, mode: "app", organizationId, organizationName, organizationUrlKey, appUserId, appUserName, scopes }`, where `scopes` lists the scopes Linear reported in the token response at install or reconnect. The adapter carries them to Core as the grant configuration `{ version: "linear-grant", scopes }`, which the Platform broker passes through unchanged. Connections installed before Ficus read them, or through a broker that does not report them, hold the requested set instead. The settings API does not return `scopes`; it returns `missingScopes`, the app scopes the connection lacks (`read` is never reported missing). A non-empty list makes the Linear card ask a workspace admin to select Reconnect. A connection whose credential does not match its configuration's mode fails validation. Every Linear call Ficus makes, and the CLI's `LINEAR_API_KEY`, use one `Authorization` value: the raw key for an API-key connection, `Bearer <access token>` for the app.

**Missing scopes at use time.** When Linear refuses a call with `Invalid scope` (code `FORBIDDEN`, sent with HTTP 400), Ficus marks the app connection **Reconnect required** with `insufficient_scope` and the card shows the same reconnect message. The acknowledgment does not retry, the outbox keeps the item waiting for a usable connection instead of marking the session inaccessible, and `--linear-session` explains that the app must be reconnected. A personal API key's permissions are managed in Linear, so an API-key connection is not marked and its outbox item fails.

## Squads and webhooks

Choose which squads use a connection right on the Linear card: each connection lists its squads (linked to their **Integrations** tabs) and offers **Add to squad**, **Add to all N squads without Linear** and **Remove** for squads where you hold squad `integrations:write`. Adding a squad that already uses another Linear connection replaces it, and the picker says so. A connection no squad uses says so with the next step. The squad's own **Integrations** tab offers the same choice. Team routing stays per squad, in the squad’s **Integrations** tab. Under **Linear Routing**, **Choose teams** opens a searchable list of the teams the squad’s attached Linear connections can see (name and key, several at once) to route assigned issues to its manager; an event rule’s **Team filter** picks one team the same way. Core lists the teams (`GET /api/squads/:squadId/integrations/linear/teams`, `integrations:read`) by querying Linear with each attached connection’s own credential, app or API key, and never sends a credential to the browser. It reuses each connection’s listing for a minute (a new credential revision lists again), stops at 5,000 teams per connection and says so, and reports a connection it cannot use or that Linear refuses beside the teams the others listed. Routing stores and matches team IDs. A saved value that is not a listed team stays visible and removable rather than dropped: one that equals a team’s key is shown as that team with a warning, since it never matched, and **Use the team ID** replaces it; any other is shown as an unknown team. When no team can be listed (no connection, or every listing failed), a team ID can still be typed in. Disabling the squad integration preserves the account choice; re-enabling restores it. Global disable preserves all account and squad settings while stopping use.

For webhook delivery, configure an Issue webhook in Linear with the URL shown in the global card and the same signing secret in both applications. Save a signing secret to enable delivery; disabling clears it. Stored secrets are never returned to the browser. Rotate by entering a new value in both places.

The connected account supplies the assignee identity. Ficus verifies current issue access, team, and assignee before delivering an event. Workflow subscriptions and squad triggers can consume the typed outputs below. When a flow handles the event, the same squad’s legacy team-based manager notification is suppressed.

## Agent CLI

A squad with an enabled, assigned Linear connection gets the `linear` command ([schpet/linear-cli](https://github.com/schpet/linear-cli), ISC license) and the `linear` agent skill (`config/skills/linear/SKILL.md`), the same way Notion provides `ntn`. Agents can view, query, create and update issues, comment, and send raw GraphQL with `linear api`.

**Installation.** The plugin's sandbox setup step installs pinned release 3.1.0 from the GitHub release assets, not from npm: the npm package `@schpet/linear-cli` is a wrapper whose install script downloads the same asset without verifying it. The step selects the `x86_64` or `aarch64` glibc Linux asset, checks its pinned SHA-256 digest before extracting anything, and refuses any other platform. Upstream ships glibc builds only, while the Docker runtime image is Alpine (musl) with amd64-only glibc compatibility. The installed `linear` is therefore a small launcher that runs the binary through the Nix glibc loader and libgcc of the pinned devbox Node.js package, which works on every Linux runtime and architecture. It has been run on x86_64 (Ubuntu and Alpine); the `aarch64` asset has been checked by digest and loader name (`ld-linux-aarch64.so.1`) but not yet run on arm64 hardware. The step needs the devbox packages `nodejs@24.12.0` (hashing and the glibc runtime) and `xz@5.8.3` (the archive format). Readiness requires `linear --version` to print `linear 3.1.0`. Host sandboxes do not reconcile a managed toolchain, so they use whatever `linear` the operator installed.

**Credentials.** `linear` is wrapped like `gh` and `ntn` (see [Integration command execution](integration-execution.md)). Each command, including one started from a script, fetches the selected connection's `Authorization` value as `LINEAR_API_KEY` for that process only: the raw key for an API-key connection, `Bearer <access token>` for the agent app. For the app, the sandbox also gets `LINEAR_ORGANIZATION_URL_KEY`, the workspace's URL key, so agents can tell which workspace the CLI acts in; API-key connections have no such binding. Nothing is written to disk, and disabling or detaching the connection takes effect on the next command; the wrapper then fails instead of running the CLI with any other credential.

**Account selection.** The CLI resolves a key from the process environment first, then a `.env` file, then `api_key` in a project or global `.linear.toml`, then credentials stored by `linear auth login` (a credentials file or the system keyring). Ficus closes each other path:

- `LINEAR_API_KEY` is always set by the wrapper, so `.linear.toml` keys and stored credentials are never consulted.
- `LINEAR_IGNORE_ENV_FILE=1` stops `.env` loading. Without it, a repository `.env` could set `LINEAR_GRAPHQL_ENDPOINT` and receive the key. The endpoint is also pinned to `https://api.linear.app/graphql`.
- `--workspace` fails with a usage error while `LINEAR_API_KEY` is set, so it cannot switch to a stored account.
- A project `.linear.toml` can still set nonsecret defaults such as the team. The skill tells agents to pass `--team` explicitly.
- The skill forbids `linear auth login` and `logout`.

A person's own terminal has no agent identity, so the wrapper runs their own `linear` login unchanged.

**App tokens.** The CLI sends `LINEAR_API_KEY` verbatim as the `Authorization` header (checked against a local server for both a raw key and a `Bearer` value), so the agent app's `Bearer <token>` needs no CLI change. With an app connection, everything the CLI writes appears in Linear as the app, not as a person.

## Outputs

Verified webhooks normalize into these typed outputs, the same way GitHub events do. They are consumable from workflow subscriptions, squad event rules and predicate conditions, including [decision conditions](github-integrations.md#decision-conditions) (`GET /api/integrations/outputs`). The organization webhook (API-key connections) delivers `Issue` and `Comment` events; the agent app's webhook also delivers agent session events.

| Output                   | Emitted when                                                                                                                                                                                                                                     | Source                                                                              |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------- |
| `issue.assigned`         | The issue's assignee changes and it now has one                                                                                                                                                                                                  | `Issue` update                                                                      |
| `issue.unassigned`       | The issue's assignee changes and it now has none                                                                                                                                                                                                 | `Issue` update                                                                      |
| `issue.updated`          | State, title, labels or another field change. `action` is `state`, `title`, `labels` or `updated`; `state` is the Linear workflow state's _type_ (e.g. `started`, `completed`). A delegate change is also reported as `issue.updated`, as before | `Issue` update                                                                      |
| `issue.comment`          | A comment is created or edited                                                                                                                                                                                                                   | `Comment`                                                                           |
| `issue.created`          | An issue is created                                                                                                                                                                                                                              | `Issue` create                                                                      |
| `issue.delegated`        | An issue gains a delegate (an agent). Delegation to the connection's own Ficus app comes from its agent session, not from the issue update                                                                                                       | `AgentSessionEvent` `created` without a human-authored root comment; `Issue` update |
| `issue.undelegated`      | An issue loses or changes its delegate; `delegate` is the removed one                                                                                                                                                                            | `Issue` update                                                                      |
| `issue.mentioned`        | The Ficus app is @mentioned on an issue                                                                                                                                                                                                          | `AgentSessionEvent` `created` whose root comment has a person as author             |
| `agent_session.created`  | Linear opens an agent session for the app (always paired with one `issue.delegated` or `issue.mentioned`, which is what the default rules route on)                                                                                              | `AgentSessionEvent` `created`                                                       |
| `agent_session.prompted` | A person sends a message into an existing session; `prompt.signal` is `stop` for a stop request                                                                                                                                                  | `AgentSessionEvent` `prompted`                                                      |

Fields on every output: `issue.id`, `issue.number`, `issue.identifier` (e.g. `ENG-123`), `issue.title`, `teamId`, `teamKey`, `assignee`, `delegate` (the delegated agent's Linear user ID), `action`, `actor`, `state`, `actorType` (`user`, `guest`, `app` or `unknown`, from a live lookup of the actor on app connections), plus the predicate-only `labels`, whose names compare case-insensitively (`contains blocked` matches `Blocked`). Extra fields: `issue.comment` has `comment.id`, `comment.parentId` and `session.id` (set when the comment is in a thread of one of the app's own sessions); `issue.delegated` has `previousDelegate` and `session.id`; `issue.mentioned` has `comment.id` and `session.id`; `agent_session.created` has `session.id`, `session.url`, `session.trigger` (`delegation` or `mention`), `session.creator`, `session.appUserId` and `comment.id`; `agent_session.prompted` has `session.id`, `session.appUserId`, `activity.id`, `prompt.signal` and `comment.id`.

Event keys come from stable Linear IDs, so a later delivery of the same fact (a retry, or the [polling fallback](#polling-fallback)) is recorded once: session facts hash the session ID, prompts the activity ID, `issue.created` the issue ID, and issue-update delegation facts the issue ID, delegate and `updatedAt`. A session event body is the issue URL plus Linear's `promptContext` (`created`) or the prompt text (`prompted`), bounded to 30,000 characters and always presented as evidence, not instructions. Sessions outside an issue produce no outputs. `AppUserNotification`, `PermissionChange` and `OAuthApp` webhooks produce no outputs. For agent app connections, the [polling fallback](#polling-fallback) recovers missed sessions, prompts and the app's own undelegations; every other output, and every output of an API-key connection, depends on webhook delivery alone.

## Event rules

Squad event rules work as for GitHub (first enabled matching rule wins; `notify-manager`, `notify-consultant`, `start-workstream` or `ignore`). Without stored Linear rules a squad gets these defaults, all limited to the squad's shared team routing (an empty route list matches nothing):

| Rule ID                         | Output                   | Action           | Account involvement     |
| ------------------------------- | ------------------------ | ---------------- | ----------------------- |
| `linear-issue-assigned`         | `issue.assigned`         | `notify-manager` | `connected-account`     |
| `linear-issue-unassigned`       | `issue.unassigned`       | `notify-manager` | `connected-account`     |
| `linear-issue-delegated`        | `issue.delegated`        | `notify-manager` | `connected-account`     |
| `linear-issue-undelegated`      | `issue.undelegated`      | `notify-manager` | `connected-account`     |
| `linear-issue-mentioned`        | `issue.mentioned`        | `notify-manager` | `assigned-or-mentioned` |
| `linear-issue-comment`          | `issue.comment`          | `notify-manager` | `assigned-or-mentioned` |
| `linear-agent-session-prompted` | `agent_session.prompted` | `notify-manager` | `connected-account`     |

`issue.created`, `issue.updated` and `agent_session.created` have no default. A squad that already saved Linear rules keeps them unchanged; its rules editor offers **Add recommended Linear rules** to append any missing default.

**Account involvement.** The account is the connection's Linear user: the app user for an app connection, and for an API-key connection the key's viewer as returned by the live access probe (recorded on the event's authority, never read from the payload).

- **Delegated or assigned to this account** (`connected-account`): `issue.assigned` and `issue.unassigned` need the account as the assignee, `issue.delegated` and `issue.undelegated` as the delegate, and `agent_session.*` need the session to belong to the account. Other outputs use the next rule.
- **This account is assigned, delegated or @mentioned** (`assigned-or-mentioned`): the author is neither the account nor another app, and the fact is an `issue.mentioned` or the account is the issue's assignee or delegate. An `issue.comment` in one of the app's own session threads does not match, because it already arrives as `issue.mentioned` or `agent_session.prompted`. Mentions of a personal API-key account on issues not assigned to it are not detected.
- **Any matching event** (`any`): no involvement needed.

Events of the four older outputs recorded before account binding existed carry no account and keep the old unrestricted behavior; the newer outputs never match an account-involvement rule without a recorded account. Comments written (`comment.author`) or triggered (`actor`) by the account itself are always suppressed (`self-comment`), because Linear turns Ficus's own session replies into comments and agents comment through the CLI.

**Upgrade.** Before agent app support, Linear ignored a rule's account involvement although the rules editor saved one on every rule. A one-time startup step (`LINEAR_RULE_AUDIENCES_MIGRATED`) therefore sets stored Linear rules to **Any matching event**, except `issue.assigned` and `issue.unassigned` rules, which ingress already bound to the account, so existing rules keep matching what they matched before. Rules saved afterwards keep the involvement they are saved with.

The rules editor shows a note that every new agent session is acknowledged whatever the rules do, and the match preview takes a hypothetical connected account ID for Linear and shows the self-comment suppression.

**Trusted authors (decision 9.4).** On app connections, only active, non-guest, non-app members of the connected Linear workspace may start work or prompt it. Ficus checks the acting user with its own live lookup (a definite answer is cached for 10 minutes per user; a failed lookup leaves the author untrusted without hiding the issue) and records the result on the event's authority, never from payload claims. A Linear event whose authority records no trust value is treated as untrusted. For anyone else, a matching `start-workstream` or `notify-consultant` rule is held: the squad manager gets the event with a note that the author is not a trusted member and the `ficus workstream create --from-event` command to start work anyway. `notify-manager` and `ignore` rules apply as usual, and a held rule with decision conditions is still evaluated so the manager is told. API-key connections have no author check: their events are recorded as trusted.

## Agent sessions

When someone delegates an issue to the Ficus app or @mentions it, Linear opens an agent session and sends an `AgentSessionEvent`.

**Delegation or mention.** Linear gives every session a root comment (`agentSession.comment`), a delegation included: for a delegation it is Linear's own thread comment, "This thread is for an agent session with ficus.", which has no author. A session is therefore a mention when its root comment has an author (`comment.userId` on the webhook, `comment.user` when polled), or when a payload has a `commentId` without the comment object. A session without a creator and without an authored root comment is one the app opened on itself, with a raw `agentSessionCreateOnIssue` outside `--linear-session`: Linear sets `creator` to the responsible person for a delegation or mention (also when an automation delegates) and leaves it unset for a session an agent user started. Such a session is recorded with trigger `proactive`, produces no outputs and gets no acknowledgment or disposition, because whoever opened it reports in it; a polled one whose issue is delegated to the app is still a delegation. The webhook's issue has no delegate field, so a session another agent user opens by delegating to Ficus would also read as the app's own. Any other session is a delegation when its root comment is missing or is Linear's thread comment, or the issue is delegated to the app; another authorless comment (a mention synced from another tool) stays a mention. `session.trigger` and `linear_agent_sessions.trigger` follow this rule (`linearSessionTrigger` in `outputs.ts`).

**Direct ingress (self-hosted).** The app webhook is `POST /api/webhooks/linear-app`, separate from the organization webhook so the two secrets, replay rules and authorities never mix. A delivery is accepted only when `Linear-Signature` is the HMAC-SHA256 of the raw body under the app's webhook signing secret (compared in constant time; without a configured self-hosted app the endpoint answers `503`), its `webhookTimestamp` is within 60 seconds, the body `type` equals the `Linear-Event` header, and, for `AgentSessionEvent`, `AppUserNotification`, `PermissionChange` and `OAuthApp`, its `oauthClientId` is the configured client ID. Rejected deliveries are stored unverified and never processed. Accepted ones are stored with their `Linear-Delivery` ID (unique per provider), answered `200` at once and processed afterwards; a repeated delivery ID is acknowledged without processing it again. The organization ID selects the enabled app connection, and session, notification and permission events must name its app user. The rows join the existing Linear Activity family.

**Hosted ingress (Ficus Cloud, relayed).** The hosted app has one webhook URL for every workspace, on Platform (`<platform>/api/integration-relay/linear/webhook`). Platform verifies each delivery and keeps it for its tenant for 72 hours; Core pulls it (`apps/core/src/services/integrations/relay/linear-runtime.ts`, wire schemas in `packages/shared/src/integration-relay/protocol.ts`):

- **Subscriptions.** Every enabled `platform_broker` app connection that does not need reauthorization is subscribed with its connection ID, material revision and access token; Platform derives the workspace and app user from the token. Connections are pulled every 2 seconds. Linear rotates access tokens daily: after a refresh (a new token revision on the same connection revision) Core subscribes again with the new token before its next pull, and a `422 linear_authorization_required` pull answer re-subscribes at once and pulls again in the same pass. Disabling or uninstalling a connection unsubscribes it.
- **One hosted instance per workspace (decision 9.1).** A `409 linear_organization_claimed` subscribe answer means another Ficus Cloud instance holds the workspace. Core stops subscribing that connection revision (no retries, including after token refreshes), records the code on the connection (`relay_subscribe_error_code` and `relay_subscribe_error_revision`) and the Linear card shows "This Linear workspace is already connected to another Ficus Cloud instance." The connection itself stays usable for agents. Reconnecting creates a new revision and subscribes again, which succeeds once the other instance lets go. A team that needs a second instance uses a self-hosted app with its own identity.
- **Processing.** Each delivery is fenced to the live connection revision and its body must name the connection's workspace and the delivery's event type. A durable receipt keyed `linear:<Linear-Delivery>` (`integration_event_polling_dispatches`; these relay receipts, and only these, are swept 7 days after completion) is claimed first, then the delivery runs the direct path's processing: a verified `linear-app` webhook row (Activity is projected from it) and the `linear-app` handlers. A redelivered delivery ID is acknowledged without processing it again; a handler error is recorded on the row, as on the direct path, while a failure before processing leaves the delivery for Platform to deliver again.
- **Trust boundary.** A relayed delivery is stored as verified on Platform's word: Core does not re-check its signature, `webhookTimestamp` freshness or `oauthClientId`, because Platform verified them against the raw Linear request before storing it. Platform's verification is the trust boundary for hosted ingress; Core's own checks are limited to the tenant-authenticated pull, the connection revision fence, and the workspace and event-type agreement above.
- **Early acknowledgment.** Core handles a pulled batch one delivery at a time, and a mention's `Comment` delivery reaches Platform before its session, so the session's acknowledgment used to wait for the comment's enrichment probe, user lookup and fan-out (a live mention was acknowledged after 9.84 seconds). Before dispatching a batch, Core now acknowledges every `AgentSessionEvent` `created` delivery in it, concurrently and under the same revision and workspace fences; the session's own processing then finds the acknowledgment sent.
- **Latency.** Linear to Platform, a 2-second pull and one acknowledgment call is about 4 seconds. While the instance is down or restarting, Platform keeps the deliveries and sessions are acknowledged late when Core pulls them.

**Acknowledgment.** Linear marks a session unresponsive without an activity within 10 seconds. Before any rule, decision condition or squad fan-out, Ficus records the session (`linear_agent_sessions`) and posts the `thought` "Received. Checking how to handle this request." once per session, whether or not any squad is assigned to the connection. The first attempt has a 2.5-second timeout, so a hung call leaves the retry most of the budget; the retry runs while `webhookTimestamp` + 9 seconds allows, with up to 4 seconds. The activity ID is derived from the session ID and a fixed projection key, so a repeat never shows twice. A missed deadline is not fatal: Linear recovers the session on the next activity.

**Routing.** One enrichment probe per event with the app token, shared by every squad on the connection, reads the issue (team, labels, assignee, delegate), the comment for comment events and the acting user. An issue the app cannot read reaches no squad. A session delegation additionally requires the probed delegate to be the app user. Each assigned, active squad then gets the facts under its own authority and its rules run. Admins should route each Linear team to one squad.

**Disposition.** After the squads' rules ran, the session gets one fixed activity:

| Outcome across squads                                                        | Activity                                                                                                     |
| ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| A `start-workstream` rule created or bound a work stream                     | `thought`: "Ficus queued this work. Progress will appear here."                                              |
| No stream, at least one manager or consultant notification                   | `response`: "Ficus passed this request to the team. Updates will appear here if work starts."                |
| Every matching rule ignored it, no rule matched, or no squad routes the team | `response`: "Ficus is not set up to take requests like this here, so no work was started."                   |
| The app cannot read the issue                                                | `error`: "Ficus cannot access this issue's team. A Linear admin can grant access in the Ficus app settings." |
| Session without an issue                                                     | `response`: "Ficus works on Linear issues. Mention or delegate Ficus on an issue."                           |
| More than 60 sessions in the workspace in the past hour                      | `response`: "Ficus is busy. Try again later."                                                                |

Texts are fixed: they never name squads, agents or internal state. A prompt on a session not bound to a stream gets the same disposition for that prompt.

**Binding a session to a work stream.** A session binds to at most one stream: when a `start-workstream` rule creates or matches a stream from a session's fact (in the same transaction as the trigger receipt), when `ficus workstream create --from-event` or `ficus workstream track --event` uses a session's fact, or when a session opens on an issue an active stream of an assigned squad already tracks under the same connection. The first committed binding wins; other streams are created without it and their trigger receipts record `session_already_bound`. The stream's tracked Linear issue gets an `agentSession: { id, url }` copy (the session table stays authoritative), and a stream's newest bound session is its primary one. Binding posts the `thought` "Ficus started tracking this work." and, only when the instance's public URL is `https:` (decision 9.5), adds an **Open in Ficus** link to the session.

**Team access and uninstall.** `PermissionChange` `teamAccessChanged` updates `linear_team_access`; when nothing is recorded yet, the first routed event or `PermissionChange` records every team the app can list (a change is applied on top of that listing, never on its own). Ingress uses it only as a fast pre-filter: an event is rejected before the probe only when a `PermissionChange` from Linear excludes its team, and a team the probe can read is added to the record. Sessions on removed teams are marked `inaccessible` and each bound stream's owner is told once. The squad Integrations tab names routed teams the app cannot access, and the Linear integration's setup status reports **Needs attention**, naming each such squad and team. `OAuthApp` `revoked` (the app was uninstalled) marks every app connection for that workspace **Reconnect required** and sends the OAuth operational alert.

### Polling fallback

Agent app connections are also polled, as a low-frequency safety net for a webhook that never arrived (an instance that was down, restarting or unreachable, or a self-hosted instance without a public URL). API-key connections are never polled.

**What polling recovers.** Each poll makes three requests with the app token, plus more session pages while it catches up on a backlog:

1. `agentSessions(first: 50, orderBy: updatedAt)`, read newest first, page by page, down to the last position. A session Ficus never recorded that Linear still shows as `pending` (the webhook never arrived), or one Ficus recorded but never gave a disposition, is processed exactly as a `created` webhook would be: it gets the acknowledgment and the disposition (late, but Linear recovers the session), and its `agent_session.created` and `issue.delegated` or `issue.mentioned` facts are routed. Sessions Ficus already handled, and unknown sessions that are no longer `pending`, are left alone.
2. `agentActivities` filtered to `prompt` activities created since the last position, oldest first: each is processed like a `prompted` webhook (`agent_session.prompted`).
3. `notifications` of type `issueUnassignedFromYou` created since the last position, oldest first: each becomes the app's own `issue.undelegated`.

**Retrying failed answers.** A session whose webhook arrived but whose acknowledgment or disposition could not be posted (Linear was failing at the time) is not routed again. Instead, each poll retries up to five such sessions of the connection from the session table: the acknowledgment first if it was never sent, then the recorded disposition if its post failed. A disposition is not posted while the acknowledgment still fails, and a session whose disposition reached Linear needs nothing more even if its acknowledgment failed. Attempts are spaced at least a minute and a quarter of the session's age apart, and stop six hours after the session opened.

Issue and comment changes (`issue.assigned`, `issue.unassigned`, `issue.updated`, `issue.created`, `issue.comment`, and delegations to other agents) are not polled, because Linear asks integrations not to poll for updates; a missed `Issue` or `Comment` webhook is not recovered. The output catalog descriptions say the same for each output.

**Cursor.** The position is stored per connection in `integration_event_polling_cursors` (resource `linear-app:<connection ID>`) as `{ version: 1, sessions: { updatedAfter, boundaryIds }, prompts: { createdAfter, boundaryIds }, notifications: { createdAfter, boundaryIds } }`. `boundaryIds` (at most 50) are the IDs seen at exactly the watermark, so items sharing a timestamp are neither skipped nor repeated. Prompts and notifications are read oldest first, so a full page continues from its newest item on the next poll; sessions are read newest first, up to five pages of 50 per poll. When more sessions changed than that (for example after a long outage), the poll keeps the sessions watermark where it was and stores where to continue as `sessions.resume` (`after`, Linear's page cursor, and the newest position already seen); the next polls read the older pages from there until they reach the watermark, which then moves to the newest position. A page cursor Linear refuses restarts the walk from the newest page. Sessions read again are not acknowledged twice: recorded sessions are skipped and the delivery receipt decides the rest. The first poll starts at the connection's install time, and after downtime the lookback is capped at 72 hours (the hosted relay's retention).

**Cadence and budget.** A connection is polled every 5 minutes while a verified app webhook arrived for its workspace in the last 15 minutes, and every 60 seconds otherwise. Polls are not jittered, failures back off for 1 to 5 minutes (longer when Linear's `Retry-After` says so), and nothing is polled while the connection is disabled, unhealthy or waiting for a token refresh, or while the Linear integration is disabled. At three queries per poll this is 180 queries per connection per hour, against Linear's 5,000; while a session backlog is read, a poll adds up to four session pages, taken only from what is left of the per-tick budget after keeping room for the prompts and notifications queries. Retries of failed answers add at most three calls per session (two acknowledgment attempts and the disposition), all reserved from the same per-tick budget before the retry starts. The acknowledgment, disposition and enrichment probe for a recovered event are the same calls a webhook would cause and are not part of that budget. Polled issues are read without their labels, which keeps each query's complexity low; the enrichment probe reads them for every routed event.

**Deduplication.** A polled session, prompt or notification claims the same delivery receipt as its webhook (`linear:session:<id>:created`, `linear:activity:<id>`, `linear:notification:<id>` in `integration_event_polling_dispatches`), so whichever path sees it first handles it and the other skips it. Polled facts also carry the same event keys as webhook facts, and are published under the same authority: the app user as `accountId` and the actor's trust from the same user probe (active, non-guest, non-app members are trusted), so a polled delegation from a guest holds a `start-workstream` rule exactly as its webhook would. The one exception is the app's undelegation: the `Issue` webhook keys it by the issue's `updatedAt` and the notification by its own time, so an `issue.undelegated` for the same issue and removed delegate within two minutes of one already recorded for the connection is dropped. The check reads before it records, so a webhook and a poll handled at the same instant could both record it; the duplicate would only repeat a manager notice.

## Progress write-back

Ficus reports a bound stream's progress into its primary Linear agent session, attaches the delivery pull request to the stream's Linear issues, routes follow-up prompts and stop requests into the stream, and mirrors the stream's questions as elicitations. It never changes an issue's workflow state, assignee or delegate; with a `closes` link, Linear's GitHub integration completes the issue when the pull request merges.

**What the session shows.** A projector compares the stream's current state with what the session already received and sends only the difference. It wakes on stream and question events (debounced 3 seconds per stream) and on a 60-second reconcile sweep, so a lost in-process event is caught up. Everything written is a fixed template; step names, participants, agent evidence, internal IDs and paths never appear. Each step is shown by its kind and position, for example "Working (step 2 of 4)", "Choosing the next step" or "Waiting for approval in Ficus".

| Stream change                                                                     | Activity                                                                                              |
| --------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| The stream runs (an event-created stream waiting for its owner shows nothing yet) | `thought`: "Started work."                                                                            |
| A flow step starts / finishes                                                     | ephemeral `action` "Started" / `action` "Finished", with the step label                               |
| A human approval step is waiting                                                  | `thought`: "Waiting for approval in Ficus." Approval is never given from Linear.                      |
| The delivery pull request appears                                                 | `action` "Opened pull request" with `owner/repo#n` and the URL, plus a **Pull request** session link  |
| A question is asked                                                               | `elicitation` (below)                                                                                 |
| A mirrored question is answered or dismissed in Ficus                             | `thought`: "Answered in Ficus: <option label>" or "Question withdrawn."                               |
| The stream is paused                                                              | `thought`: "Paused."                                                                                  |
| Recovery is exhausted and a person must decide                                    | `error`: "Ficus hit a problem and a person on the team is looking at it."                             |
| No activity for 25 minutes on a running stream                                    | ephemeral `thought`: "Still working: <step label>." (Linear marks a session stale after 30)           |
| Done                                                                              | `response`: "Done. Pull request: <url>." or "Done." (with the stream link when there is a public URL) |
| Canceled                                                                          | `response`: "Ficus stopped working on this request."                                                  |

Flow steps that finished before the session was bound are not shown. "Open in Ficus" and every other Ficus link are added only when the instance's public URL is `https:` (decision 9.5); a session bound before one was configured gets the link on the next projector pass.

**Outbox and limits.** Every write goes through `linear_activity_outbox`, keyed by connection, scope (the session ID, or `issue:<id>` for attachments) and a stable projection key such as `flow:<attempt>:completed` or `pr:<url>`, so re-running the projector never sends anything twice. The activity ID sent to Linear is derived from the session and projection key; a retry after an unknown outcome reuses it, and Linear's duplicate-ID rejection counts as sent. Items for one session are sent in order. Limits: 1,200 writes per connection per hour and 30 activities per session per hour; when a bucket is empty, pending progress for a session collapses to the newest item, while responses, errors, elicitations, attachments and session links are never dropped. HTTP 429 pauses the whole connection for `Retry-After`. Failures retry with backoff (5 seconds, doubling to 10 minutes, 8 attempts). A permission error marks the session `inaccessible`, stops writes to it and tells the stream's owner once.

**Pull request attachments.** When `metadata.codeHost.changeRequest` is set, Ficus calls `attachmentLinkGitHubPR` for every Linear issue the stream tracks under a Linear connection assigned to its squad (both connection modes; an API-key attachment is created as the key's owner), and for the primary session's issue. The link kind comes from the squad's **Pull request links** setting:

```json
{
  "integrationSettings": { "linear": { "version": 1, "pullRequestLinks": { "origin": "closes", "tracked": "links" } } }
}
```

`origin` applies to the issue the stream was started from (the tracked issue whose `origin.eventId` is the stream's `integrationSource.eventId`, else the primary session's issue) and `tracked` to every other tracked issue. Both accept `closes`, `contributes` or `links`; the defaults are `closes` and `links`. Edit it in the squad Integrations tab (Linear section) or with `ficus squad set-meta <squad> integrationSettings.linear '<json>'`; squad metadata writes validate it, and `GET /api/squads/:squadId/integrations/linear` returns the effective value as `settings`. The kind is resolved when the attachment is queued, so changing the setting affects later attachments only. Agents still put the issue key in branch names and pull request text, so Linear's GitHub integration recognizes the pull request even if the attachment fails.

**Prompts and stop.** A tracked Linear issue subscribes to `agent_session.prompted`, `issue.delegated` and `issue.undelegated` as well as its issue events, so a message in any session on the issue reaches the stream once, through the tracked delivery. Comments in a session thread are delivered only as the prompt (`issue.comment` facts carry `comment.inSession`, and the tracked comment subscription skips those). A Linear **Stop** from a trusted member (decision 9.4) pauses the bound stream at once with the same pause as `ficus workstream pause` (reason "Stopped from Linear by <name>"), tells the stream's owner, and answers "Stopped. Work is paused in Ficus."; only someone in Ficus can resume it. A stop from anyone else pauses nothing: the owner is told and the session gets "Your stop request was passed to the team." Prompts on a session whose stream is done or canceled go through the `linear-agent-session-prompted` rule like an unbound session's.

**Questions as elicitations.** A new human question from a bound stream becomes an `elicitation` with the question text and context (bounded to 4,000 characters) and "Reply here or answer in Ficus."; a single `select` or `multi-select` question adds Linear's `select` signal with its options. A reply answers the question directly only when all of these hold: the question is a single `select` or `multi-select`, the reply is an exact match (one option value or label for `select`; option values or labels separated by commas or new lines for `multi-select`; case-insensitive, trimmed), the author is a trusted member, and the author's Linear account is linked to a Ficus user who may answer the asking agent in Ficus (the same check as the answer route). Ficus then records it with `answerAgentQuestion` as that user's answer, with `answer_provenance` naming the Linear session and activity. Every other reply while the question is open reaches the asking agent as a candidate answer from the named Linear user, which the agent may close with `ficus agent-question resolve` using the session URL as the source. A Linear answer never satisfies an approval gate.

**Linking a Linear account.** In **Settings → Account → Linear account**, a person links their Linear account with a user-actor, `read`-only authorization of the same Ficus Linear app (purpose `linear_identity`, adapter `linear-identity`). Ficus stores the Linear user and workspace IDs in `user_linear_identities` and revokes the token at once; one Linear account belongs to at most one Ficus user. Self-hosted instances use their own Linear app's credentials and callback; hosted instances go through the Platform broker. When an unlinked member replies to an elicitation and the instance has an `https:` public URL, the session's next elicitation carries Linear's `auth` signal pointing at that settings page.

**Streams without a session.** A stream that tracks a Linear issue without a session gets the pull request attachment only. On an app connection, `ficus workstream track <ws> --issue KEY-123 --linear-session` opens a session on the issue (`agentSessionCreateOnIssue`), binds it to the stream and announces the binding, so progress appears from then on. API-key connections have no agent sessions; agents may comment through the CLI under the `linear` skill's rules.

## Authority model

A verified signature proves the payload came from Linear; it does not by itself authorize any squad to see it. The organization webhook serves API-key connections only: squads on an agent app connection never receive its events, because the app's own webhook delivers the same issues and comments with its probe and author check. For every squad with an enabled, assigned API-key connection, Ficus queries that squad's own connection to confirm it can currently read the issue (and, for `issue.assigned`/`issue.unassigned`, that the connected account is the assignee being added or removed) before publishing the event under that squad's authority, with the probed viewer recorded as the event's account. A comment payload names only the issue, so the same probe supplies its team, assignee and delegate for team routing and account involvement. For the agent app, one probe per event with the app token serves every squad on that connection, as described in [Agent sessions](#agent-sessions). A squad whose connection cannot read the issue never receives it.

## Tracked issues

Work streams can track Linear issues the same way they track GitHub issues and pull requests — see [Work references: tracked issues and pull requests](work-streams.md#tracked-issues-and-pull-requests). Linear-specific notes:

- Identity: `{ integration: "linear", repository: <team key, lowercase>, kind: "issue", number, externalId: <Linear issue UUID> }`. `externalId` is what actually holds a subscription together: a comment delivery carries only the issue UUID, not the team key or number, so a tracked issue matches on `externalId` when it is known and falls back to team key + number only when it isn't.
- Reference forms: `KEY-123` (`ficus workstream track <ws> --issue KEY-123`) or a Linear issue URL (`https://linear.app/<workspace>/issue/KEY-123[/slug]`).
- Linking resolves the issue through the squad's own Linear connection (a live `describe` GraphQL lookup), which is also how `externalId` and `url` get recorded. No usable connection → `409 Linear connection needs revalidation before linking`; the issue is unreadable or doesn't exist → `404`; the squad has no Linear connection assigned → `403`.
- Pull requests are not supported for Linear: `ficus workstream track --pr` or `--delivery` against a Linear reference is rejected with `400`, and a Linear issue can never be a delivery change request.
- A tracked issue subscribes to `issue.assigned`, `issue.unassigned`, `issue.updated`, `issue.comment` (skipping comments in an agent session thread), `issue.delegated`, `issue.undelegated` and `agent_session.prompted`, with ids `tracked-<12 hex>-<event>` derived from the resource's identity.
- `ficus workstream create --from-event <id>` and `ficus workstream track --event <id>` work for every Linear notification, including comments. An assignment or update fact carries the team key and number, so its `Tracked resource:` line reads `issue KEY-123`; a comment fact carries only the issue UUID, so the line names that UUID and the issue is resolved through the squad's own Linear connection at link time (the same `describe` lookup, with the same `409`/`404`/`403` answers).
- Trigger-created streams (`start-workstream` squad rules) record the issue in `metadata.tracked[0]`, including rules on `issue.comment` — for those the entry is completed through the squad's connection when the stream is created, and is simply omitted if that connection cannot read the issue then. Streams created before this feature may still carry the legacy `metadata.linear.issueId` correlation instead; that path keeps working for those streams, but there is no backfill converting them to `tracked` entries.

## Activity

Linear issue and comment webhooks project into the squad's Activity feed (`squad_activity`, `linear-issue` family, lane 71, kind `issue`). Assignment, state, title, label, and generic-update facts come from `Issue` webhooks; new and edited comments come from `Comment` webhooks. One row is written per stream that tracks the issue — a stream matches through its `tracked[]` entry's `externalId`, or, for older streams, the legacy `metadata.linear.issueId` — so a squad with no stream tracking the issue gets no rows, however the receipt was owned. A squad with team routing configured (`metadata.linear[].teamId`) owns the receipt even when no stream names the issue yet, which is what lets a row appear later once a stream starts tracking it; a `Comment` delivery carries no `teamId` at all, so comments are only ever owned through a tracking stream. There is no polling path for Linear Activity — only the webhook; the agent app's polling fallback routes outputs but writes no Activity rows.

Live memory search resolves the calling squad’s selected connection. Existing memory grants and team-key filters further restrict search. `ficus integration exec linear --squad <id> -- <command>` supplies the selected key (and the fixed CLI settings above) to any other command without exposing it in CLI output.

On upgrade, a legacy `LINEAR_API_KEY` is imported once as a disabled account. Validate, enable, and assign that account in Integrations. The old webhook secret is moved into encrypted integration settings. `LINEAR_USER_ID` and legacy secret editing are retired. Existing team routing metadata is preserved.
