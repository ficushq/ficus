# Hosted Core as a non-root service user: audit and migration plan

Status: audit and plan only. Nothing in this document changes runtime
behaviour; every code or toolkit change it proposes is a follow-up (listed in
[Follow-up changes](#follow-up-changes)). Rootless Docker is out of scope:
where Core uses the host's Docker daemon, the service user joins the `docker`
group.

Audited at `main` c155f243 (2026-10-26), with ficushq/ficus#678 (open) read
for the pooler account.

## Implementation status (2026-10-27)

F2, F3 and F4 are implemented, with two revisions agreed on 2026-10-27 that
replace F5 and F6, and host hardening in the same change:

- **Operator entrypoints (replaces F5).** The four entrypoints in 1.4 no
  longer run as root on a service-user host: each refuses any account but the
  owner of Core's HOME (`apps/core/src/lib/infra/operator-identity.ts`), and
  the platform runs them through `scripts/setup/run-core-operator.sh`, which
  reads `<dest>/.env` and `/etc/ficus/managed.env` as root and runs the
  entrypoint as `ficus-api`'s `User=`. The env files are parsed, not
  shell-sourced (`set -a; . .env` would run the hosted DSN's
  `&sslrootcert=…`). The box-reprovision journal moves to
  `<HOME_DIR>/box-reprovision`. Nothing is chowned after creation.
- **VAPID (replaces F6).** The `config/vapid.json` compatibility write is
  gone everywhere; the read stays for old self-hosted installs.
- **Hardening.** `sshAuthFailures` in each usage sample, so the platform can
  alert. fail2ban with an sshd jail is opt-in only (`host.fail2ban: true`, for
  a self-hosted core on an open port) and off by default everywhere, hosted
  cores included: their sshd is reachable only from the control plane, so a
  ban could only lock the platform out, and the hosted machine hosts are
  firewalled to the core and the control plane. When enabled, `setup-host.sh`
  sets it up in its preflight and fails on an error; `upgrade-host.sh` sets it
  up only after the new release is serving and only warns on an error.

Where the implementation departs from the plan below:

- A revert, and a rollback after step 7, give HOME back to the user the run
  started from (2.2 rollback step 3 said leave it): the entrypoints run only
  as HOME's owner, so a root host with a `ficus`-owned HOME could not run them.
- Caddy joins `ficus-bigbrain-client` through a unit drop-in
  (`SupplementaryGroups=`), so the membership exists whenever Caddy starts,
  including when its package is installed after BigBrain. The installer
  restarts a running Caddy whenever its process lacks the group (read from
  `/proc/<MainPID>/status`), then checks the new process has it. Normally that
  is once per host; an install whose restart failed is retried by the next.
- The BigBrain installer learns the Core account from one argument,
  `install --core-account <user>`, which the toolkit passes when
  `core.run_user` is not root.
- The switch's backup set (step 1) holds the sudoers rules whenever they
  exist, and a rollback runs the success checks for the user it went back
  to; a rollback that fails them keeps its journal. HOME moves with
  `rename(2)` only (never `mv`, which copies on `EXDEV`), and P4 compares
  mount points as well as devices.
- `sshAuthFailures` reads consecutive whole-second journal windows, counts
  lines as they stream and stops at 1 MiB or 10 s, reporting the count so
  far as a lower bound; a failed read never leaves a backlog for the next.
- After a revert, the inert service account keeps its groups (`docker`,
  `ficus-bigbrain-client`, `systemd-journal`), and managed BigBrain's
  `/etc/ficus/bigbrain` and read-handoff directory stay readable by its group
  until the BigBrain installer runs again; remove them by hand if the host
  stays on root (`gpasswd -d ficus <group>`, `chmod 0700` the two
  directories, `chmod 0600` their files).

## Why

The hosted layout leaves `core.run_user` empty and runs `setup-host.sh` as
root, so `RUN_USER` falls back to `root` and `ficus-api` / `ficus-worker` run
with `User=root`. PgBouncer refuses to start as root, which is why
ficushq/ficus#678 gives the pooler its own system account. The decision is to
move Core itself onto an unprivileged service user, `ficus`, after launch. This
document lists everything that depends on Core being root today, and the
switch plan that keeps each of them working.

## Execution contexts

The User= switch changes only context A. A sudoers entry is only ever needed
for something context A does.

| Context                                                    | Runs as today                                      | Runs as after the switch | Examples                                                                                                                                                                           |
| ---------------------------------------------------------- | -------------------------------------------------- | ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A. `ficus-api`, `ficus-worker` (systemd `User=@RUN_USER@`) | root                                               | `ficus`                  | everything in 1.1                                                                                                                                                                  |
| B. Toolkit scripts the platform runs over ssh              | root                                               | root (unchanged)         | `setup-host.sh`, `upgrade-host.sh`, `enable-pooler.sh`, `apply-artifacts.sh`, `retarget-backup.sh`, `retarget-origin.sh`                                                           |
| C. Core operator entrypoints the platform runs over ssh    | root                                               | root (unchanged)         | `dist/box-control.js`, `dist/machine-bootstrap.js`, `dist/box-reprovision.js`, `dist/system-token-control.js`; `dist/migrate.js` and `dist/rebase-home.js` run by the toolkit      |
| D. Other units on the core host                            | root / own accounts                                | unchanged                | `ficus-backup` (root, no `User=`), `ficus-pgbouncer` (the pooler account, see 2.3), `caddy` (caddy), BigBrain vault/gateway units (their own accounts), the BigBrain root launcher |
| E. Commands Core sends to machine hosts over SSH           | the machine's SSH user, with `sudo` on the machine | unchanged                | `box-control` kill/systemctl, storage scanner, box provisioning                                                                                                                    |

Contexts B and C need no sudoers entry: they already run as root. They matter
to this audit only where they create or rewrite files that context A later has
to read or write (rows T6, T7, T11, T12, O2).

Context E is not a core-host privilege: `sudo` there runs on the machine host
under the machine's SSH account, whatever user Core runs as locally.

## Part 2 — migration plan

### 2.1 New hosts

**Config.** The platform renders `core.run_user: ficus` in the
`ficus-setup.yaml` it pushes. No other key changes. `HOME_DIR` derives from
the user's home, as it does today.

**`setup-host.sh` additions** (F2):

1. **Predict the home at parse time.** `RUN_USER_HOME` is resolved when the
   config is read (`setup-host.sh:282-289`), before any phase runs, and both the
   backup check (:301) and `resolve_layout_globals` (:439) need it. When
   `core.run_user` names a user that does not exist, set `RUN_USER_HOME` to the
   home the toolkit will create, `/home/<user>`. This is deterministic and
   changes nothing on the host, so `--dry-run` and validation stay
   mutation-free. The dry run prints:
   `create system user ficus (home /home/ficus, shell /usr/sbin/nologin, groups systemd-journal[,docker])`.
2. **`ensure_run_user`** (lib.sh, next to #678's `ensure_pooler_user`),
   called from `phase_preflight` in place of the die at :995-996:
   - `RUN_USER` = `root`: nothing (the self-hosted root default stays as is).
   - Missing: `useradd --system --create-home --home-dir /home/<user> --shell /usr/sbin/nologin --user-group <user>`.
     `--system` keeps it out of the login uid range, and `nologin` because
     every toolkit use goes through `runuser -u`, which does not use the
     user's shell. The home must end up `/home/<user>`, mode 0750 (or
     0700), owned by `<user>:<user>`. `useradd`'s mode comes from
     `HOME_MODE` in `/etc/login.defs`, so the function sets it explicitly
     (`install -d -m 0750 -o <user> -g <user> /home/<user>`) and does not
     rely on the distro default. A world-traversable home would recreate
     the exposure that rules out opening `/root` (R10).
   - Existing (created now or earlier): `usermod -aG` for the groups in 1.6
     that apply. Group membership is the only thing it ever changes on an
     existing account, and it only adds: `usermod -aG` never removes a
     group. A host that moves off a docker runtime therefore keeps `docker`
     membership (root-equivalent) until someone removes it. That is
     accepted: removing groups the toolkit did not add could break an
     operator's own setup, and runtime changes are rare, manual operations.
     The runtime-change procedure should include `gpasswd -d <user> docker`.
   - Then the existing `ensure_system_bun_node` cross-user smoke test runs as
     before.

   Trade-off: a typo in `core.run_user` now creates an account instead of
   dying. The dry-run line and a `log_info` make that visible, and an
   explicit opt-in key would cost every self-hoster a second setting for
   little gain, so the recommendation is to create it.

3. **`phase_services`** already installs `/etc/sudoers.d/ficus-update` for a
   non-root user. **`bigbrain_install`** installs the second sudoers line and
   the grants R4-R6 when BigBrain is enabled (F3).
4. **`install_artifacts`**: group-readable for the service group (R7).
5. **`phase_restore`**: chown the restored HOME (T12).
6. **`phase_report`**: assert `systemctl show -p User --value` is `<user>`
   for both units.

`.env` and the release trees stay root-owned (F1, F8). Core creates its HOME
on first start as `ficus` (`ensureHomeDir`) inside `/home/ficus`. The pooler
runs as `ficus`, and `ficus-pgbouncer` is never created (2.3).

### 2.2 Existing hosts: switch-run-user.sh

A new toolkit script (F4) in the shape of `enable-pooler.sh`. The platform
ships it with `lib.sh` and the systemd templates and runs it over ssh as root
(F7).

**Timing.** The switch happens after launch, one tenant at a time, each in its
own maintenance window. It is not a fleet-wide sweep: each run is checked (S1-S10
and the manual post-checks) before the next tenant starts. The restart is the
same kind of interruption as an upgrade: running executions are requeued by
the worker's normal shutdown.

```
switch-run-user.sh --config /root/ficus-setup/ficus-setup.yaml [--user ficus]
switch-run-user.sh --config /root/ficus-setup/ficus-setup.yaml --revert
```

It takes nothing secret on the command line or stdin: the direct DSN comes from
`<dest>/.env`, as in `enable-pooler.sh`. It is idempotent. Its last line is
`FICUS_RUN_USER=<user>` (`ficus` after a switch, `root` after a revert or a
rolled-back failure).

**Preconditions.** Refuse and change nothing unless all of these hold:

| #   | Check                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P1  | euid 0; `require_host_layout_ready`, `require_host_env_ready`; `host_migrate_lock` taken; no journaled host migration (`PENDING` absent)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| P2  | Artifact layout (`<dest>/current` resolves to a complete release)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| P3  | Either not yet switched (config `core.run_user` empty or `root`, units `User=root`), or already switched (config says `<user>`, units `User=<user>`, old HOME absent, new HOME present). In the second case only the success checks run, and then the trailer prints                                                                                                                                                                                                                                                                                                                                                                                                                    |
| P4  | The old HOME (from `.env` `HOME_DIR`) exists. The new HOME `/home/<user>/.ficus` is absent or an empty directory. `stat -c %d` of both parents is equal, so the move is one `rename(2)`. Otherwise it dies with: `refusing: <old HOME> and /home/<user> are on different filesystems — this switch moves HOME with a single rename and never copies it; nothing was changed`. The switch never falls back to a copy: a copy doubles disk use, races a live HOME and needs its own verification. The operator leaves that host on root (still fully supported) and reports it. A host with a separate `/home` needs its own plan, for example a service-user home on the root filesystem |
| P5  | No symlink inside the old HOME has an absolute target under the old HOME (`find "$OLD" -type l -lname "$OLD/*"`). Such links would dangle after the move; the script lists them and refuses                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| P6  | `rebase-home.js --dry-run --from "$OLD" --to "$NEW"` reports no `REBASE_HOME_TARGET` rows (nothing already stored under the new HOME in a structured column; free-text mentions in `messages.metadata` and `work_streams.files` are reported as `REBASE_HOME_TARGET_TEXT` and do not count)                                                                                                                                                                                                                                                                                                                                                                                             |
| P7  | `ficus-backup.service` is not running                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |

**Steps.** Each step is recorded in a step journal in the root 0700 host backup
root before it runs. An interrupted run is settled from that journal, forward
or back, and never guessed from directory state (the `host_migrate` doctrine).

1. Back up every file this run rewrites (both unit files, their drop-in
   directories, the host config, `.env`, the backup script, any sudoers file,
   and the pooler ini, userlist and unit) into a backup set, as
   `host_migrate_backup_create` does.
2. `ensure_run_user` (the same function as 2.1): create `ficus` with its groups.
3. Stop `ficus-backup.timer`, `ficus-api`, `ficus-worker`, then the pooler unit
   if enabled.
4. `mv "$OLD" "$NEW"` (`/root/.ficus` → `/home/ficus/.ficus`).
5. Rebase the stored paths: `_hl_rebase_home "$ENV_FILE" <current release> "$OLD" "$NEW"`.
   The services are stopped and the rebase uses the direct DSN.
6. `envfile_set "$ENV_FILE" HOME_DIR "$NEW"`. `.env` stays root 0600.
7. `chown -R --no-dereference ficus:ficus "$NEW"`. This covers everything a
   root Core and its containers wrote, whatever its owner: Core's own
   entries (`sessions`, attachments, `skills`, `ssh`, `machines`), and on
   docker-runtime hosts the files containers wrote with the image's uid
   under `workspaces/` and `private/`, plus the shared nix base
   `nix/.base` and its per-sandbox clones (hardlinks share an inode, so
   one chown covers every link) (R9). `--no-dereference` changes symlinks
   themselves and never follows one out of the tree. `chown -R` does not
   follow symlinked directories by default, so nothing outside `$NEW` is
   touched. Then make sure `"$NEW"/machines`, `machines/keys` and
   `machines/ctl` exist, owned by `ficus`, 0700 (O2). The same
   `find "$NEW" -xdev ! -user ficus` that proves this step is success check
   S3.
8. Record `core.run_user: ficus` in the host config (`as_root yq -i`; T6).
9. File artifacts: `chgrp ficus` and `chmod g+r` on each file under
   `/etc/ficus/artifacts/` that has owner read (R7). The next `apply-artifacts`
   run keeps this, through F2's `install_artifacts`.
10. `install_update_sudoers` (visudo-validated), plus the BigBrain line when
    `/etc/ficus/bigbrain/host.json` exists.
11. Pooler, if `database.pool.enabled`: `install_pooler "$(envfile_direct_dsn "$ENV_FILE")" <size> <reserve> <templates>`.
    It re-renders the unit with `User=ficus` and re-owns the directory, ini and
    userlist (2.3). Its own start and port wait run here, before the core
    units start.
12. BigBrain, if installed: `bigbrain_install` with the Core account, so it
    applies R4-R6 (F3).
13. Re-render the backup script: read the live values with
    `backup_script_read_values`, replace `HOME_DIR` only, and install it with
    `render_backup_script_content`, 0755 root (T11).
14. `install_core_units` (`User=ficus`), `ensure_managed_env_dropins`,
    `ensure_api_memory_guardrail`, `systemctl daemon-reload`.
15. `restart_core_services <port>`: the shared health wait (`GET /health`
    200/401, then worker active with `NRestarts` holding still). Then start
    `ficus-backup.timer`.
16. Run the success checks below. On any failure, roll back.
17. Remove the step journal and the backup set, then print
    `FICUS_RUN_USER=ficus`.

**Success checks** (all must pass before the trailer):

| #   | Check                                                                                                                                                                                                                    |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| S1  | `systemctl show -p User --value` is `ficus` for `ficus-api` and `ficus-worker`, and each `MainPID` belongs to `ficus` (`ps -o user= -p`)                                                                                 |
| S2  | `restart_core_services` passed (health and the worker crash-loop guard)                                                                                                                                                  |
| S3  | `test ! -e "$OLD"`, and `find "$NEW" -xdev ! -user ficus` prints nothing                                                                                                                                                 |
| S4  | `rebase-home.js --dry-run --structured-only --from "$OLD" --to "$NEW"` reports 0 rows on every structured column (`REBASE_HOME`), run before the restart (step 15); free-text mentions (`REBASE_HOME_TEXT`) do not count |
| S5  | `runuser -u ficus -- journalctl -u ficus-api -n 1 --no-pager` prints a line                                                                                                                                              |
| S6  | `runuser -u ficus -- sudo -n -l` lists exactly the commands in 1.6 for this host                                                                                                                                         |
| S7  | With the pooler: `systemctl show -p User --value ficus-pgbouncer` is `ficus` and `127.0.0.1:6432` accepts connections                                                                                                    |
| S8  | The installed backup script's `HOME_DIR` is `$NEW` (`backup_script_read_values`)                                                                                                                                         |
| S9  | `runuser -u ficus -- test -r` passes for every file artifact, and for `host.json` on BigBrain hosts                                                                                                                      |

After the trailer, outside the script: the machines page shows every machine
`ready` and a box terminal opens (R11); a test push reaches an iOS device on
tenants with APNs (R7); `systemctl start ficus-backup.service` succeeds and the
new archive contains the HOME tree (T11); BigBrain tenants create and delete a
scratch vault (R3-R6).

**Rollback** (`--revert`, and the automatic path for any failure after step 3):

1. Stop `ficus-api` and `ficus-worker`, and the pooler.
2. If step 5 ran: `_hl_rebase_home "$ENV_FILE" <current> "$NEW" "$OLD"` (the
   inverse run).
3. If step 4 ran: `mv "$NEW" "$OLD"`. Ownership is left as `ficus`: root reads
   any owner, so a chown back would only add a second recursive rewrite.
4. Restore the backup set: units, drop-ins, host config (`core.run_user` empty
   again), `.env`, backup script. Remove the sudoers files this run added. Put
   the artifact groups back to `root`.
5. With the pooler: `install_pooler` with `RUN_USER=root`, so it renders the
   pooler account again (2.3).
6. `systemctl daemon-reload`, `restart_core_services`, start
   `ficus-backup.timer`, print `FICUS_RUN_USER=root`.

The `ficus` account itself is left in place: it owns nothing that runs, and
leaving it makes a retry cheap.

### 2.3 The pooler account

With ficushq/ficus#678, `pooler_user` prints `${RUN_USER}` whenever it is not
`root`, and the pooler account name (`ficus-pgbouncer`) only for root.
`install_pooler` passes that user to `ensure_pooler_user` (a no-op for an
existing account), to the directory, ini and userlist ownership, and to the
unit's `User=`. After step 11 of the switch, or on a new host with
`core.run_user: ficus`, the pooler runs as `ficus` again: one owner for the
ini, the userlist, the unit and Core, as before #678. This depends on #678
merging first (F1).

**Leave `ficus-pgbouncer` in place on the switch.** After step 11 it owns no
process and no file. It has no home and no shell, so it is inert. Removing it
in the same window gains nothing, and the revert path would only recreate it
(`ensure_pooler_user`) with a new uid. Remove it later in a fleet-wide cleanup,
once no switched host can still revert: on each host, `pgrep -u ficus-pgbouncer`
and `find / -xdev -user ficus-pgbouncer` are both empty, then
`userdel ficus-pgbouncer`. Hosts provisioned with `core.run_user: ficus` never
create it.
